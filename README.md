PayFlow 
========

Overview
--------

PayFlow is a simplified fintech backend system inspired by applications like PhonePe and Google Pay.This project provides REST APIs for:

*   Registering users

*   Viewing users

*   Searching users by UPI ID

*   Recording money transfers between users


The project is built using:

*   Spring Boot

*   Spring Web

*   Spring Data JPA

*   H2 Database


The application is fully backend-based and communicates entirely through HTTP APIs.

Layer Explanation
=================

1\. Entity Layer
----------------

The entity layer represents database tables using Java classes.

Example:

*   User

*   Transaction


These classes are annotated with @Entity, allowing Hibernate/JPA to automatically create tables in the H2 database.

2\. Repository Layer
--------------------

The repository layer handles database operations.

Interfaces like:

UserRepository extends JpaRepository<User, Long>

allow CRUD operations without writing SQL manually.

Spring Data JPA automatically generates SQL queries internally.

3\. Service Layer
-----------------

The service layer contains business logic.

Examples:

*   Registering users

*   Fetching users

*   Sending money transactions


Controllers communicate with services instead of directly accessing repositories.

4\. Controller Layer
--------------------

The controller layer exposes REST APIs.

Examples:

*   POST /users

*   GET /users

*   POST /transactions


Controllers receive HTTP requests and return JSON responses.

Spring Boot Features Used in This Project
=========================================

1\. Embedded Server
-------------------

Spring Boot comes with an embedded Tomcat server.

In this project, no external Tomcat installation was required.Running the main() method automatically started the application on port 8080.

Console output:

```
Tomcat started on port 8080
```

This demonstrates Spring Boot's embedded server feature.

2\. Auto-Configuration
----------------------

Spring Boot automatically configured:

*   H2 Database

*   Hibernate/JPA

*   Dispatcher Servlet

*   Tomcat Server


based on the dependencies added in pom.xml.

For example:

*   Adding spring-boot-starter-data-jpa automatically configured Hibernate and DataSource.

*   Adding H2 Database dependency automatically connected the in-memory database.


No manual XML configuration was needed.

3\. Production-Ready Defaults
-----------------------------

Spring Boot provides sensible default configurations that reduce setup complexity.

Examples in this project:

*   Automatic JSON conversion using Jackson

*   Embedded Tomcat configuration

*   Automatic table creation using Hibernate

*   Default error handling

*   Dependency injection using @Autowired


These defaults allowed the application to run with minimal configuration.

JPA Derived Query Method
========================

Repository Method:

````
User findByUpiId(String upiId);
````

Hibernate internally generates SQL similar to:

````
select * from users where upi_id = ?
````

Explanation:

*   Spring Data JPA derives the query automatically from the method name findByUpiId.

*   The ? symbol is a placeholder parameter that gets replaced with the actual UPI ID value during execution.


JPQL Query Example
==================

````
@Query("SELECT u FROM User u WHERE u.balance > :amount") 
List<User> findUsersWithBalanceGreaterThan(@Param("amount") Double amount);
````

This query uses:

*   Entity name (User)

*   Java field name (balance)


instead of table names and column names.

Custom Query Approaches in Spring Data JPA
==========================================

1\. Derived Query Methods
-------------------------

Example:

```
findByUpiId(String upiId)
```

Spring automatically generates queries based on method names.

Best for simple queries.

2\. JPQL Queries
----------------

Example:

```
@Query("SELECT u FROM User u WHERE u.balance > :amount")
```

Uses entity classes and Java fields.

Best for medium-complexity queries.

3\. Native SQL Queries
----------------------

Example:

````
@Query(value = "SELECT * FROM users", nativeQuery = true)
````

Uses raw SQL directly.

Least preferred because:

*   Database-dependent

*   Harder to maintain

*   Breaks database portability

*   Bypasses some JPA abstraction benefits
